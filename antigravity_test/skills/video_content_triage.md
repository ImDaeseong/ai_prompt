# Skill: Video Content Triage (영상 콘텐츠 트리아지)

> ID: SKILL-TRIAGE-001 | Version: 1.0 | Last Updated: 2026-09-25

사용자가 유튜브 영상 설명·자막·AI 생성 요약을 붙여넣고 "이거 반영할 수 있는지 확인하시오"라고 물을 때 쓰는 워크플로다. 목적은 영상을 홍보하거나 요약하는 것이 아니라, **이 워크스페이스에 실제로 반영할 가치가 있는지**를 증거 기반으로 판정하는 것이다.

> **다른 스킬과의 차이:** `hermes-agents`의 형제 저장소인 `ai-workspace`의 `dev/AI_VERIFICATION_CHECKLIST.md`(이 스킬이 있는 `ai_prompt` 저장소가 아니라 `ai-workspace` 저장소 안에 있다)는 환각·인용 검증의 일반 체크리스트를 제공한다. 이 스킬은 그 체크리스트를 "영상에서 시작된 반영 여부 판단"이라는 구체적 반복 작업에 적용한 절차다. 각 판정은 그 체크리스트의 규율을 따른다.

## 0단계 — 내용이 실제로 있는가부터 확인한다

붙여넣은 텍스트에 타임스탬프와 챕터 제목만 있고 각 항목의 실제 설명이 없는 경우가 흔하다("팁 1", "1단계" 같은 라벨뿐). AI 생성 요약도 "토큰 효율·워크플로 개선" 같은 매우 일반적인 문구뿐일 수 있다.

**판정 기준:** 구체적인 주장·수치·방법·코드·설정이 최소 하나도 없으면 0단계에서 멈춘다. 없는 내용을 일반 지식으로 채워 "이 영상이 말하는 것"처럼 서술하지 않는다 — 이는 실제로 존재하지 않는 시나리오를 창작하는 것과 같다. 사용자에게 실제 자막/스크립트를 요청하고 종료한다.

## 1단계 — 이름 충돌부터 배제한다

영상이 언급하는 프로젝트·도구 이름이 이 워크스페이스의 실제 프로젝트 이름과 같을 수 있다(`Hermes Agent`가 이 저장소 `hermes-agents`와 무관한 서드파티 트레이딩 제품이었던 사례). 이름이 같다고 관련 있다고 가정하지 않는다. 웹 검색으로 그 이름의 실제 정체를 먼저 확인한다.

## 2단계 — 주장을 영상이 아니라 1차 출처로 검증한다

영상의 나레이션이나 AI 생성 요약을 그대로 사실로 받아들이지 않는다. 각 핵심 주장에 대해:

- 언급된 저장소/도구가 실존하는지 확인한다 (`WebSearch`/`WebFetch`).
- 라이선스를 주장할 때는 자동 감지기가 아니라 실제 `LICENSE` 파일 원문을 읽어 확인한다.
- 날짜·버전·수치가 영상의 주장과 일치하는지 확인한다.
- 인용된 1차 출처(공식 블로그, 저자 본인 글, 공식 문서)를 직접 찾아 대조한다. 제3자 요약에서만 확인되고 원문을 대조하지 못했다면 `[LOW-EVIDENCE]`로 표시한다.
- 저장소 자체가 주장하는 성능/벤치마크 수치는 벤더 자기보고로 취급하고 독립 근거로 쓰지 않는다.

## 3단계 — 이미 있는 것과 중복인지 확인한다

새 도구/기법이 검증됐다고 바로 채택하지 않는다. 이 워크스페이스에 같은 역할을 하는 것이 이미 있는지 먼저 찾는다.

- MCP 서버/스킬 후보라면 `.mcp.json`, 기존 스킬 색인을 먼저 확인한다.
- 이미 같은 문제를 해결하는 도구가 있다면, 새 도구가 명백히 우월하지 않은 한 **Context Confusion**(CLAUDE.md) 위험이 채택 이익보다 크다 — 기록만 하고 채택하지 않는다.
- 이미 이 저장소의 규칙(AGENTS.md)이나 기존 스킬이 같은 원칙을 더 구체적으로 다루고 있다면, 영상은 "독립적 확인"으로만 취급하고 새 규칙을 추가하지 않는다.

## 4단계 — 위험 영역을 가장 먼저 걸러낸다

금융·법률·세무·노동·계약·의료 위험이 있는 콘텐츠(예: 실거래 자금이 걸린 자동매매)는 몇 단계를 거치기 전에 바로 플래그한다. 이런 영역에서는 전문 자문이 아니라는 점을 밝히고 전문가 검토가 필요함을 알리며, 추상적 설계 원칙만 분리해 평가하고 구체적 실행(실제 자동매매 코드 등)은 채택하지 않는다.

홍보성 채널(제휴 링크·유료 커뮤니티·"이거 하나면 끝" 톤)은 자동으로 배제하지는 않지만 검증 강도를 높이는 신호로 다룬다.

## 5단계 — 판정과 기록

세 가지 결과만 있다.

| 판정 | 조건 | 행동 |
|---|---|---|
| **반영(Adopt)** | 검증된 실제 공백이 있고, 중복이 아니며, 위험 영역이 아님 | 해당 스킬/AGENTS.md/문서를 최소 범위로 수정 → 관련 테스트/가드 실행 → 통과 후 커밋. 같은 검증이 두 번 실패하면 접근을 바꾸고, 세 번째 반복 전에 HOLD한다(AGENTS.md Escalation Rules) |
| **기록만(Record-only)** | 실존하지만 중복이거나 이미 반영돼 있음, 또는 근거가 약함(`[LOW-EVIDENCE]`) | 저장소는 변경하지 않는다. 메모리에 근거·판정 사유를 남긴다 |
| **거절(Decline)** | 내용이 없거나(0단계), 위험 영역이거나, 검증 실패 | 사용자에게 이유를 설명하고 종료한다. 필요시 이름 충돌 등 주의사항만 기록 |

**반영이든 기록만이든 판정을 조용히 넘어가지 않는다.** 매 트리아지마다 최소한 메모리 항목 하나(무엇을 검토했고 왜 그렇게 판단했는지, 검증에 쓴 실제 도구 호출 근거 포함)를 남긴다. "반영(Adopt)" 판정은 실제 커밋과 검증 통과 로그가 있어야 완료로 본다 — 말로만 "반영하겠습니다"는 완료가 아니다.

## 안티패턴

1. **타임스탬프뿐인 설명에서 내용을 지어내기** — 실제로 없는 팁 목록을 일반 지식으로 채우는 것.
2. **영상 자체를 근거로 인용하기** — 영상이 아니라 영상이 가리키는 1차 출처를 인용한다.
3. **이름이 같다고 같은 프로젝트로 가정하기** — 항상 실제 정체를 먼저 확인한다.
4. **검증 없이 "실존확인 완료"라고 쓰기** — 실제 `WebSearch`/`WebFetch` 호출 없이 아는 지식으로 대체하지 않는다.
5. **중복 도구를 "더 낫다니까" 추가하기** — Context Confusion 비용을 항상 먼저 계산한다.
6. **판정을 아무 기록 없이 끝내기** — record-only도 결과다. 메모리에 남기지 않으면 다음 세션이 같은 영상을 또 검토하게 된다.
